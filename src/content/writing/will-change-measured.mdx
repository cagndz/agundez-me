So I tried it on the next component, a dial, and there it did almost nothing. I wanted to understand why before putting it anywhere else.

## What the browser does with a frame

Roughly, every frame goes through four steps:

- **Style**: work out which CSS applies to each element.
- **Layout**: work out sizes and positions.
- **Paint**: record what to draw, and then **raster** it: turn that record into pixels, tile by tile.
- **Composite**: put the finished layers on screen, each in its place.

The page is split into layers, and each layer is rastered on its own. Chrome does the raster work on helper threads and the compositing on a compositor thread, away from the main thread where your JavaScript runs. [Mariko Kosaka explains this really well](https://developer.chrome.com/blog/inside-browser-part3).

`transform` and `opacity` are special. If an element has its own layer, the compositor can move, turn, scale or fade that layer without painting or rastering it again. It's like sliding a printed photo across a table instead of drawing it again in every position.

The catch is that "if". Without its own layer, the element is part of the layer underneath, and moving it means repainting that layer. Switch between the two below:

## Who tells the browser

There are two ways to animate a `transform`.

With a CSS animation, a CSS transition or the Web Animations API (WAAPI), you hand the whole animation to the browser up front. It knows what's going to move, so it gives the element its own layer and runs the animation on the compositor. That's what people usually mean by hardware acceleration.

With JavaScript and `requestAnimationFrame`, you write a new value into the style on every frame. The browser doesn't know an animation is happening. It just sees a style change, again and again, on the main thread.

The demo below shows the main thread part. Both cards run the same turn: the left one is a Web Animation, the right one is written frame by frame from JavaScript. The button keeps the main thread busy for one second, the way a long task would.

<MainThreadDemo />

The left card keeps turning because nothing in its animation needs the main thread. The right one freezes, then jumps to where it should be once the thread is free.

That's the part you can see. The part you can't see is the layer. An element animated from JavaScript doesn't get one by default, so on every frame it changes, the browser repaints and rasters the layer it lives in. `will-change: transform` tells the browser ahead of time: the element gets its own layer, and the compositor can move it without repainting it.

## The card

The wallet is built with [Motion](https://motion.dev). The animation has two phases, rise and then turn, and it has to survive a click in the middle of either one. So I drive it with motion values and `animate()`:

```tsx
const y = useMotionValue(0)
const rotate = useMotionValue(0)

animate(rotate, -90, { type: 'spring', duration: 0.55, bounce: 0.2 })

return <motion.div style={{ y, rotate, willChange: 'transform' }} />
```

To put numbers on it, I opened and closed one card in headless Chromium 141 through Playwright, recorded a trace and added up the raster work. Each number is the average of three runs. Headless numbers aren't what you'd get on a phone, so compare them with each other, not with your device.

The shadow was the surprise. It's a blurred silhouette on a layer of its own, so it can keep pointing down while the card turns. Without a layer of its own, that blur was rastered again on every frame, and blur is expensive to raster. That's most of the 185 ms.

I want to be honest about the trail, though. Raster runs on helper threads, not on the main thread, and 185 ms spread over almost two seconds of animation is under 2 ms per frame on my machine. The trail was mostly the speed of the turn: at its fastest, the card rotates about 10 degrees between two frames at 60 Hz. The repaint was extra work on top, not the cause. It would matter more on a slow phone.

## The Motion docs said otherwise

This is where I got stuck. Motion's [performance page](https://motion.dev/docs/performance) says independent transforms like `x`, `scale` and `rotate` "are hardware accelerated, just like animating `transform` directly". If that was true, why did my card repaint?

There were two reasons, one about versions and one about the API.

That acceleration shipped in [Motion 14.2.0](https://motion.dev/changelog?lib=motion), on October 13, 2026. My repo was on 13.4.4, and the docs already describe the new version. [Emil Kowalski's animation standards](https://github.com/emilkowalski/skills/blob/main/skills/review-animations/STANDARDS.md) say the opposite, that the `x`/`y`/`scale` shorthands "run on the main thread via rAF". That was true before 14.2.

The second reason holds even on the latest version. Motion can only hand an animation to the browser when it animates a CSS property of an element. A motion value created with `useMotionValue` and animated with `animate(value, …)` isn't tied to an element or a property. In the source, Motion starts that animation with an empty property name, the check for hardware acceleration fails, and it falls back to its JavaScript loop.

I checked it with a card that moves and turns, counting the WAAPI animations on the element and the raster tasks:

- `animate(element, { x, rotate })`: not accelerated in 13.4.4 (about 90 raster tasks), accelerated in 14.6.0 (3).
- `<motion.div animate={{ x, rotate }} />`: not accelerated in 13.4.4 (89), accelerated in 14.6.0 (3).
- `animate(element, { transform })`: accelerated in both (3).
- A motion value animated with `animate(value)`: not accelerated in either (about 90).
- The same motion value with `will-change: transform`: 0.

So for the wallet, upgrading Motion wouldn't remove the need for `will-change`. The choreography needs motion values.

## The dial

The dial is a wheel with 101 ticks. You drag it to turn it, and the ticks near the center grow and fade in as they pass.

Giving the wheel its own layer didn't change the number of raster tasks. The wheel moves as a whole, but what's inside it changes on every frame: the ticks scale and fade. A layer whose content changes has to be rastered again anyway.

Promoting every tick fixes that, at the cost of more than a hundred layers.

Each one takes GPU memory, and the [web.dev guide on layers](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count) is blunt about it: "Do not promote elements unnecessarily." The dial was spending well under half a millisecond per frame on raster to begin with, so I left it as it was.

## What I do now

- I measure first. Paint flashing shows what repaints, and the Performance panel shows what the raster costs.
- I use `will-change: transform` on elements that move as a whole and are animated from JavaScript: motion values, springs, drag, gestures.
- I don't use it on elements whose content changes while they move. The layer doesn't help there.
- When an animation can be a CSS transition, a CSS animation or a WAAPI animation, I let the browser handle the layer.
- I write down versions. The library I use changed this exact behavior a few days before I measured it.

[MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/will-change) calls `will-change` "a last resort to try to deal with existing performance problems". After all this, I agree. Find the problem first.
